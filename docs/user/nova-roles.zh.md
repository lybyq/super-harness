# Harness 角色组合与角色团队

[English](nova-roles.md) | 中文

## 先分清两种用法

角色组合让一个聊天按多种职责工作；角色团队会创建多个独立 agent（智能体），分别执行任务。先配置好模型、选择项目并创建聊天，再打开 AI Hub 的角色界面。Hub 必须有可选的基础角色；空列表需要部署人员在 Hub 配置角色，不是安装一个额外插件就能自动出现。

| 你的需求 | 选择什么 | 实际发生什么 |
|---|---|---|
| 一个助手兼顾前端、测试或产品要求 | 单会话角色组合 | 合并职责与能力，应用到一个空闲会话 |
| 前端与测试分别工作、各有模型与结果 | 多 Agent 角色团队 | 创建成员会话，分配任务与依赖 |
| 已有默认角色不完全适合自己 | 自定义模板 | 选基础角色，再增删能力与补充工作约定 |

## 一、使用单会话组合

从一个空闲聊天开始，按下面顺序操作。应用角色不等于立即调用模型。

1. 打开 AI Hub → 角色，加载并勾选基础角色，例如前端与测试。
2. 点击“解析组合”，检查能力、必需项与冲突。此步骤只预览，不安装、不启动任务。
3. 在“自定义角色与团队”选择“单会话角色组合”，填写模板 ID、名称和“职责与工作约定”。ID 使用小写字母、数字、连字符等合法资源 ID。
4. 根据需要填写增加、移除、停用能力与包含可选项，使用 Hub 中真实能力 ID，多个 ID 用逗号分隔。移除被其他能力依赖的项可能产生冲突，不会强行忽略。
5. 保存模板，选择“目标会话”，点击“应用角色与能力”。缺少能力会走统一安装链路；需要账号的项先在配置页填完必填参数。
6. 回到该聊天发出任务。新的职责在下一条消息中进入模型上下文；安装成功不代表 Jira、Wiki 等账号一定有业务权限。

模板保存在当前桌面，并不自动上传到 Hub。想让同事共用基础角色，须在 Hub 管理其角色记录。切换职责不会清除历史聊天；差异很大的角色建议新建聊天，以免旧上下文混杂。

## 二、启动角色团队

团队成员可能同时调用模型，需要预先确认费用、账号与项目写权限。团队是独立执行，不只是多角色提示词。

1. 勾选要参与的基础角色，在模板中选择“多 Agent 角色团队”。
2. 为成员设置模型时，提供方与模型名称必须同时填写；不填写时使用当前可用默认选择。可以设置输出 token 上限、最大步骤数与独立 worktree。
3. 在“共享任务与依赖（JSON）”填写任务图，或者保留空数组由团队任务驱动；这里目前是 JSON 编辑区，不是可拖拽流程图。
4. 保存模板、选择空闲目标会话，填写“团队任务（必填）”，点击“启动角色团队”并确认。
5. 打开官方团队面板与“查看团队任务与工作树”，查看成员、依赖、状态和产出。若只有部分成员成功创建，先检查已有成员，不要反复点击启动。

下面是假设 Hub 真实角色 ID 分别为 `frontend`、`tester` 的任务图；请替换成你实际勾选的 ID。`member` 填角色 ID，`dependsOn` 填任务 ID，不填成员会话 ID。

```json
[
  { "id": "implement", "subject": "实现页面", "description": "实现页面并自测，提交代码与说明", "member": "frontend", "dependsOn": [], "writeScopes": ["apps/web"] },
  { "id": "verify", "subject": "验收页面", "description": "等实现完成后检查功能和回归风险", "member": "tester", "dependsOn": ["implement"], "writeScopes": ["tests"] }
]
```

缺少依赖、循环依赖、不存在的角色和非法相对路径会在创建前拒绝。`writeScopes` 是成员之间的协作声明，不是操作系统文件 ACL，也不构成沙箱。真正的限制仍来自 Harness 工具权限、项目访问权限与服务端账号权限。

## 三、审阅团队代码

只有需要分别改代码时才启用独立 worktree。项目必须是已有提交的 Git 仓库，主项目已有改动不会被自动覆盖。

成员完成后，先查看团队信息，选择成员工作树，点击“审阅成果 Diff”。确认提交内容与测试结果后，填写要合并的具体提交并执行合并；当前合并链路是显式 cherry-pick 单个提交，不会自动把所有成员代码拼进主项目。冲突需要在 Git 中处理，不要把“任务完成”当成“合并完成”。

## 四、能力与权限如何进入会话

角色解析得到能力集合，桌面共用安装、版本检查与配置验证链路。MCP 通过官方 MCP Client 启动或连接；skill（技能）通过官方 Skill Provider 注册；Host Plugin 通过原生插件系统加载。角色职责通过官方 Agent 注入入口进入会话，而不是修改 Agent Loop 或替换所有系统提示词。

| 看到的情况 | 去哪里处理 |
|---|---|
| 有基础角色，但组合解析冲突 | 调整角色能力与自定义增删项，再解析 |
| 能力需要账号或 URL | AI Hub → 已安装 → 详情 → 配置参数 |
| 已填账号，但服务返回拒绝 | 检查 Jira／Wiki／GitLab 的服务端权限与地址 |
| 目标会话不可应用 | 等当前运行结束，或新建聊天后刷新会话列表 |
| 团队按钮失败 | 检查默认模型、任务文字、团队 Provider 与 Git 条件 |
| 角色停用了工具 | 调整角色能力；不要绕过原生工具权限或业务 ACL |

Role Access 控制可见与可执行工具，但不能把同一个可信宿主插件进程变成多租户隔离容器。需要强隔离时，应使用受控账号、独立 Host／操作系统账户与沙箱部署，不能只靠角色名称。

## 开发与验收

新增业务能力先按[能力开发规范](../nova-capability-development.zh.md)开发、验证并发布，再在 Hub 角色引用真实能力 ID。日常构建、重启与带入内网见[离线开发手册](../cookbook/nova-offline-development.zh.md)。在真实内网模型上完成“应用组合后调用一个只读工具”“两个成员按依赖执行”“worktree 审阅与合并”验收后，才能向团队宣称对应流程已验证。

## 开发备注

任务图的配置仍是 JSON；真实角色 ID、模型名称、权限与团队费用由内网部署负责人验收。本教程不把配置保存成功等同于真实模型运行成功。
